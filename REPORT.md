## 1. Реализация Redis-кэша
_TODO: Опишите, что именно кэшируется и с какими ключами._

Нужно указать:
- ключ каталога;
- ключ карточки заказа;
- TTL;
- логику cache hit/miss.

Кэшируются два типа данных:

**Каталог товаров:**
- Ключ: `catalog:v1`
- TTL: 60 секунд
- Источник данных: агрегат по таблице `order_items` — топ 100 товаров по количеству продаж

**Карточка заказа:**
- Ключ: `order_card:v1:{order_id}`
- TTL: 30 секунд
- Источник данных: таблицы `orders` и `order_items`

**Логика cache hit/miss:**

При запросе с `use_cache=true`:
1. Смотрим в Redis по ключу
2. **Cache hit** — возвращаем данные из Redis, поле `source=cache`
3. **Cache miss** — загружаем из БД, кладём в Redis с TTL, возвращаем данные с `source=db`

При запросе с `use_cache=false`:
- Всегда идём в БД, Redis не используется
```python
# Cache hit
cached = await self.redis.get(key)
if cached:
    return json.loads(cached)  # возврат из Redis

# Cache miss — загружаем из БД и кладём в кэш
data = await load_from_db()
await self.redis.set(key, json.dumps(data), ex=ORDER_CARD_TTL)
return data
```

**Где генерируется событие:**

В endpoint `mutate-with-event-invalidation` после успешного UPDATE в БД:
```python
# После изменения в БД публикуем событие
event_bus = CacheInvalidationEventBus()
await event_bus.publish_order_updated(
    OrderUpdatedEvent(order_id=str(order_id))
)
```

**Где обрабатывается событие:**

В классе `CacheInvalidationEventBus` в методе `publish_order_updated`:
```python
async def publish_order_updated(self, event: OrderUpdatedEvent) -> None:
    # Инвалидируем карточку заказа
    await self.redis.delete(order_card_key(event.order_id))
    # Инвалидируем каталог
    await self.redis.delete(catalog_key())
```

**Какие ключи инвалидируются:**
- `order_card:v1:{order_id}` — потому что изменилась сумма конкретного заказа
- `catalog:v1` — потому что агрегат каталога может зависеть от данных заказов

Запуск теста:
```bash
docker compose exec -T backend pytest app/tests/test_payment_rate_limit_redis.py -v -s
```

**Policy:** 5 запросов за 10 секунд с одного IP адреса.

**Ключ лимита:** `rate_limit:pay:{client_ip}` — по IP адресу клиента.

**Реализация через Redis INCR + EXPIRE:**
```python
count = await redis.incr(key)       # увеличиваем счётчик
if count == 1:
    await redis.expire(key, 10)     # устанавливаем окно при первом запросе
if count > limit:
    return JSONResponse(status_code=429, ...)
```

**Поведение при превышении:** возвращается `429 Too Many Requests` с телом:
```json
{"detail": "Too many requests. Please try again later."}
```

**Заголовки в ответе:**
- `X-RateLimit-Limit` — максимальное количество запросов в окне
- `X-RateLimit-Remaining` — сколько запросов осталось
- `Retry-After` — через сколько секунд можно повторить (при 429)

**Результат теста:**

Попытка 4: ✅ | remaining=1 | limit=5
Попытка 5: ✅ | remaining=0 | limit=5

## 6. Выводы
_TODO: Сформулируйте 3–5 практических выводов._

Рекомендуется осветить:
1. Когда кэш даёт выигрыш, а когда нет.
2. Почему инвалидация сложнее, чем кэширование.
3. Почему rate limiting полезен даже при наличии бизнес-валидаций.

1. **Кэш даёт максимальный выигрыш для тяжёлых агрегирующих запросов.** Каталог ускорился в 7+ раз потому что запрос к БД требует агрегации по 400 000 строкам. Для простых SELECT по первичному ключу выигрыш меньше, но всё равно значительный за счёт экономии на сетевом round-trip к БД.

2. **Инвалидация сложнее чем кэширование.** Добавить кэш просто — один вызов `redis.set()`. Инвалидация требует понимания всех зависимостей: изменение заказа может влиять на карточку заказа, на каталог, на агрегаты пользователя. Пропустить хотя бы один ключ — клиент получает stale data. Это одна из самых сложных проблем в распределённых системах.

3. **Stale data — реальная проблема для финансовых данных.** В нашем тесте без инвалидации клиент видел сумму 500.0 вместо актуальной 999.0. В реальном маркетплейсе это может привести к тому что пользователь видит неверную сумму заказа и принимает решения на основе устаревших данных.

4. **Rate limiting нужен даже при наличии бизнес-валидаций.** Бизнес-логика защищает от двойной оплаты конкретного заказа. Rate limiting защищает инфраструктуру от шторма запросов — DDoS, случайного цикла в коде клиента, автоматических повторов. Это разные уровни защиты.

5. **TTL — страховка от забытой инвалидации.** Даже если инвалидация по событию не сработала, данные устареют через 30-60 секунд автоматически. TTL не заменяет инвалидацию, но ограничивает время жизни stale data.
